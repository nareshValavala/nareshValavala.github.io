The mechanism

Two paths, because Claude Code can't be written to directly

Reading is easy: a daemon tails Claude Code's own session log and relays it up. Writing isn't. Claude Code has no API for injecting a reply, and hooks don't fire on a session that's sitting idle. A VS Code extension solves it by typing the reply into the terminal directly.

Built for one person, one session at a time, as a POC while working on AnalyzeMyOffer. The pattern isn't Claude Code specific. It should extend to any AI tool with a proper access point.

Decisions Chosen / rejected

A few of these reversed an earlier decision after it failed in practice. That's in the record on purpose.

Polling, not Realtime

Supabase Realtime kept hitting a TIMED_OUT bug on the RLS channel. Switched to plain polling, about every 1.5 seconds.

Rejected: Realtime subscriptions, after they proved unreliable in practice.
A VS Code extension, not hooks

Hooks looked like the natural way to inject a reply, but they don't fire on an idle session, which is exactly when you need one.

Rejected: the hook-based write path, after it failed to wake a stalled session.
Email and password, not magic link

One less round trip to a phone that's already the whole point of the tool.

Rejected: magic-link auth, for the extra friction on mobile.
No signup flow

Single user, admin-provisioned account. There's no one else this needs to onboard.

Rejected: an open signup flow this tool doesn't need.
Where it stands
BuiltDaemon, web app, VS Code extension, Supabase relay, auth, session isolation. I used it myself while building AnalyzeMyOffer, away from my desktop.
UntestedNo automated tests, a deliberate call for a single-user v1. Verified by using it, not by a test suite.
PublicCommitted and pushed. No automated tests, verified by using it.

The honest limit

This works because I used it, not because a test suite proved it. It was built for exactly one person and one session at a time, and it's never pretended to be more than that.
